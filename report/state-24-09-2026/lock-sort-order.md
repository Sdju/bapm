# Порядок записей в lock

**Статус:** намеренно  
**Класс:** намеренное отличие  
**Важность:** низкая — меняется только порядок строк, пины и семантика lock те же; шум в diff предсказуем и устраняется одним переписыванием.  
**Проверено:** 08-11-2026, working tree

## Суть

Один и тот же набор зависимостей APM и bapm записывают в lock в разном порядке. APM сортирует по глубине в дереве разрешения `(depth, repo_url)`, OpenAPM требует лексикографический порядок по identity пакета `(repo_url, virtual_path)`. Содержимое пинов может совпадать полностью, а diff lock-файла — быть большим.

bapm канонизирует порядок при каждой сериализации: `serializeLockfile` фильтрует self-запись и сортирует массив через `compareDeps` (`packages/core/src/modules/Lockfile/serialize.ts:15-18`). Компаратор сначала сравнивает `repo_url`, затем `virtual_path` (`serialize.ts:102-108`); `depth` в сортировке не участвует. Поэтому порядок не зависит от того, в каком порядке резолвер обошёл граф.

Практическая цена — не семантика, а байты. Любая запись lock (install, update, `lock`) переписывает весь блок `dependencies`, даже если изменился один пин. Для команды, которая перешла с `apm`, это разовый большой diff; дальше порядок стабилен. Если `apm` позже перезапишет lock, он вернёт свой порядок по глубине.

## Влияние

- **Сценарий:** в репозитории лежит `apm.lock.yaml`, сгенерированный `apm`; первый `bapm install` переписывает его.
- **Кого задевает:** команда и ревьюеры lock, mixed-tooling CI, автор PR.
- **Последствие:** большой diff только из-за перестановки записей; ревью становится шумным, но пины и работоспособность не меняются.
- **Частота:** при каждом переключении инструмента или первой записи lock после `apm`; внутри одного bapm — один раз.
- **Обходной путь:** принять разовую канонизацию и не переключать инструменты; либо сравнивать lock семантически, игнорируя порядок.

## Вариации

1. Сохранять порядок APM, чтобы `apm` ↔ `bapm` не шумели в git; минус — bapm перестаёт быть детерминированным относительно порядка обхода и расходится со своей спекой.
2. Порядок OpenAPM (текущий выбор); **рекомендуется** — детерминированный вывод и соответствие `req-lk-005`.
3. Не пересортировывать чужой lock, пока пины не менялись — не сделано: любой write канонизирует порядок; плюс — меньше diff, минус — два режима сериализации.

## Рекомендация

Оставить вариант 2. Это требование OpenAPM и уже существующий контракт сериализатора; переключение на порядок APM даст нестабильный вывод. Оценка S: код и тесты менять не нужно, достаточно закрыть карточку как намеренное отличие.

Критерии закрытия:

- [ ] вариант 2 подтверждён владельцем;
- [ ] в docs явно сказано, что первый `bapm install` может дать большой diff только из-за порядка;
- [ ] тест сортировки остаётся зелёным.

## Поведение сейчас

Каждая запись lock bapm переписывает `dependencies` в порядке `(repo_url, virtual_path)`. Lock, который принёс `apm`, после `bapm install` может дать большой diff только из-за перестановки; пины при этом не меняются. Если `apm` перезапишет lock, порядок снова станет по глубине. Ошибок и предупреждений о смене порядка нет — это молчаливая канонизация.
