# Поле `origin` во внутреннем MCP-объекте

**Статус:** открыто  
**Класс:** баг (риск утечки в конфиг агента)

## Суть

При сборе серверов bapm помечает каждый как `origin: "direct" | "dependency"`. Это служебное поле. В lock его вырезают. В объект, который уходит в `configureMcp`, оно остаётся.

## Состояние

| Источник     | Позиция                                                                                                                                             |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| APM          | В конфиге хоста такого поля нет.                                                                                                                    |
| OpenAPM      | Конфиг MCP — command/url/env/headers, не provenance.                                                                                                |
| Спека bapm   | Lock inventory не должен тащить внутренние ключи.                                                                                                   |
| Код bapm     | `Mcp/collect.ts` ставит `origin`. `Mcp/lockInventory.ts` фильтрует `origin` при записи lock. `configureMcp` получает исходный `CollectedMcpServer`. |
| Документация | Не описывает `origin` как пользовательское поле.                                                                                                    |

## Вариации

1. Срезать `origin` перед `configureMcp` (как уже сделано для lock).
2. Оставить и надеяться, что интеграция копирует только известные ключи.
3. Явно документировать и писать в lock — ломает чужие MCP JSON.

## Поведение сейчас

Lock чистый. Попадёт ли `origin` в `.cursor/mcp.json`, зависит от интеграции: Cursor по ключу `origin` не ищет, но если сериализатор копирует rest-поля объекта, ключ окажется в JSON. Это не проверено по всем хостам.
